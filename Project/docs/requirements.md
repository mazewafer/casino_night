# Requirements — Team <NN>

## User stories
*As a <role>, I want <capability> so that <benefit>. The "so that" is what lets you judge
later whether a proposed change actually serves the purpose.*

## Domain model
*The entities, their attributes, and the relationships between them. A diagram is fine;
so is a table. What matters is that a reader can tell what things exist in your system.*

## Use cases
*For each significant one: actor, goal, preconditions, main flow, alternative flows,
exceptions, postconditions. The exceptions are where the thinking is.*

## Non-functional requirements
*Performance, dependability, security, privacy. Give numbers where you can — an untestable
non-functional requirement is a wish.*
